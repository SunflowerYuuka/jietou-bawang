# 数值推导 — 批次 A（`astrum:hiyori` / `rei` / `kurumi` / `saren` / `mimi` / `muimi`）

本文是 task 43a 的推导记录。权威数据是 `K:\AI\Minecraft\assets\bwiki_按角色\<id>_<name>\角色数据.json`，
每一招都是一条**公式**；本文把每条公式算到本 mod 的一个数，并逐条说明它落到哪个效果、为什么，以及哪些
从句**没有承载机制**（记录，不静默丢弃）。

**锚点一个字都没改**：参考等级 **208**、参考攻击力 **2000**、锚点 = 姬塔自己的 UB
`4.8×2000+60+60×208 = 22140 → 20.0`（`docs/balance-derivation.md` §14.1）。所以全批次共用一条换算：

```
伤害值  = round1( 20.0 × 公式(Lv208/A2000) / 22140 )
攻击档  = clamp(round(公式值 / (0.20×2000)), 1, 5)      # 每档 +20% 攻击力
防御档  = clamp(round(公式值 / (0.12×2000)), 1, 5)      # 每档 12% 减伤
减益档  = clamp(round(公式值 / (0.20×2000)), 1, 4)      # 每档 20%，四档
呼吸档  = clamp(round(u / 4), 1, 5),  u = 20.0 × 公式值 / 22140   # 一档 = 参考血条 20 点的 20%
充能点  = TP / 10                                        # 1 充能点 = 10 TP（§14.5 的换算，不是比例）
```

round1 用**四舍五入到一位小数**（与 `BwikiTraceabilityTest` 的 `Math.round(v*10)/10` 同一口径；本批次恰好
有两个 `.x25` 的边界，见 §6 的 2.2500 → **2.3**、16.2499 → **16.3**）。

## 0. 三条全批次约定（本批次新定，与 §14 不冲突）

**(a) bwiki 的半径单位 → 方块。** bwiki 写的是游戏内的半径（200/225/275/280/300/400/500/575/600/700/900），
本 mod 的效果半径是方块。约定 `方块 = clamp(round(R/100), 4, 10)`，即 200–400 → 4、500 → 5、575–600 → 6、
700 → 7、900 → 9；「我方全体」一律用 `AttackBuffs.PARTY_RADIUS_DEFAULT = 8.0`（§4 的既有值），
「自身」一律 `0.0`。这是**距离常量**，不是数值强度，和 §14.2 的伤害无关。

**(b) 6★ 技能改名从哪来。** `角色数据.json` 只给 `技能1..技能2 / 特殊技能 / 专属` 的公式，**不给 6★ 技能1 的
名字与公式**；名字在 `技能图标\` 目录的标签里：`技能1_强化1_<名>+` 是专武档、`技能1_强化2_<名>++` 是 6★ 改名档
（日和莉 キャットストライク++、胡桃 ブレイブリーベル++、咲恋 ファイアスラッシュ++、美美 ぴょんぴょんアタック++、
矛依未 ビビらせてやる！++、怜 的技能2 カウンタースラッシュ+）。**所以 tier3 的名字有出处，tier3 的公式没有出处**：
沿用 tier2 的数、只换名字，这是记录在案的缺口（§7 汇总）。怜没有 强化2 标签，tier3 与 tier2 同名。

**(c) 生命值上限 → 原版 `minecraft:health_boost`。** 本 mod 没有「最大生命」这个 `EffectType`。按佩可莉姆的先例
（§15.4.3：`amp a = 4×(a+1)` 点生命，一条 20 点参考血条 = amp 4，超过一条血条的一律夹到 **amp 4**）：
怜 的 1125、胡桃 的 15750 / 16875 都远超 20，全部 **amp 4**。

**没有承载机制的从句（记录）**

1. **击晕 5.5 秒 → `panic` 1.5 秒**。`panic` 的阶梯只有一档、固定 1.5 秒（§9 记录过同一个差异）。这是原版的
   控制时长与本 mod 的控制时长不等，不是漏算。
2. **6★UB 的「每秒恢复…持续18.5秒」是真正的持续回血（task 63 修正本条）**。本条曾写着「改成一次性
   `heal_area` 1 档」，理由是 `UbEffect` 装不下 `ally_effect` 的 `duration`/`amplifier` —— 那个理由已经
   不成立：`UbEffect` 现在带 `vanillaEffect` 与 `amplifier` 两个字段，时长走 `effectParams.seconds`，所以
   落 `ally_effect` = `minecraft:regeneration`（§12 的原版机制本身）、amp 0、18.5 秒、半径 4。
   **剩下的近似只有比率**：`regeneration` 的强度是档位而不是「每秒 N 点」，最低一档 amp 0 是每 50 刻回
   1 点（0.4/秒），而原文 247.2 raw/秒 = u 0.223/秒 —— 18.5 秒合计约 7.4 点，比率高约 1.8 倍；**时长精确**。
   见 `Task63ResourceTest`．
3. **tier3 的名字有出处、公式没有**：`ブレイブリーベル++` 沿用 tier2。

**没有承载机制的从句（记录）**

1. **「改为行动模式2，期间每秒消耗100技能值」**（本体与 6★UB 都有）：**task 48 已接入** —— 机制本体是
   `CharacterDef.ub.secondRotation`（见 `docs/balance-derivation.md` §19 与 `task-48-report.md`）。人类裁定
   ①「直接消耗掉全部」意味着气槽在施放瞬间清零（`UbTransaction.decide` 本来就这么做），所以数据里只表达
